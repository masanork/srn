# 提案：Web/A Governance Workflow (WGW)

**ステータス**: ドラフト (Draft)
**日付**: 2026年1月1日
**起案者**: 開発チーム

## 1. 背景と課題

Sorane プロジェクトは「真正性のあるWeb文書」を提唱しているが、そのプロジェクト自体のウェブサイト更新や仕様変更といった重要な意思決定プロセスは、GitHub 上の「いいね」やチャットログといった、**中央集権的かつ永続性の乏しい手段** に依存している。

特に、以下のようなリスク管理において、開発者のセルフチェックのみに依存する現状のフローには限界がある：
*   **コンプライアンス**: 「50年保証」といった過大な表現や、不適切な用語の使用。
*   **セキュリティ**: 監査未了の仕様へのリンク公開。
*   **透明性**: 「誰が」「いつ」その変更を承認したかの証跡が、プラットフォーム（GitHub）にロックインされている。

## 2. 提案内容：Approval as Code

我々が開発している **Web/A (Web Archive format)** 技術そのものを、組織のガバナンス・プロセスに適用する（ドッグフーディング）。
具体的には、サイト更新や仕様変更の「承認プロセス」を、**Web/A 形式の『稟議書』の流通** として再定義する。

### 2.1. ワークフロー概要

1.  **申請 (Request)**:
    *   開発者は変更内容（Git diff等）を含む **「変更申請書 Web/A」** を生成する。
    *   これには開発者の署名 (L2) が付与される。
2.  **回覧と承認 (Review & Approve)**:
    *   ガバナンス委員は、送付された HTML ファイルをブラウザで開く。
    *   内容を確認し、問題なければブラウザ上の「承認」ボタンを押下する。
    *   委員の Passkey (WebAuthn) を用いて、新たな署名を含む **「承認証明書 (Verifiable Presentation)」** が生成される。
3.  **執行 (Execution)**:
    *   CI/CD パイプラインは、リポジトリに提出された「承認証明書」を検証する。
    *   有効な承認署名が含まれている場合のみ、本番環境へのデプロイ（マージ）を自動実行する。

## 3. 技術的構成要素

### 3.1. Web/A Form for Governance
既存の `Web/A Form` 技術を応用し、以下の機能を持つテンプレートを開発する：
*   **Diff Viewer**: 変更前後の差分をグラフィカルに表示するコンポーネント。
*   **Multi-Sig Logic**: 規定数（例：2名以上）の承認署名を集めるためのロジック。

### 3.2. Headless Verifier (CI/CD)
GitHub Actions 上で動作する検証器。
*   提出された Web/A ファイルから署名を抽出し、事前に登録された「ガバナンス委員公開鍵リスト (DID)」と照合する。

## 4. 期待される効果

1.  **ドッグフーディングの加速**: 自組織の運営自体が、Web/A の強力なユースケース実証となる。
2.  **ガバナンスのポータビリティ**: 承認履歴が単一の HTML ファイルとして保存されるため、GitHub がサービス終了しても「意思決定の歴史」が失われない。
3.  **非エンジニアの参加**: CLI や Markdown を扱えない委員でも、ブラウザさえあれば承認プロセスに参加可能となる。

## 5. ロードマップ

*   **Phase 1 (Manual)**: リリース判定会議用の「議事録兼承認書」を手動で作成し、Web/A として署名・保管する運用を開始。
*   **Phase 2 (Automated Gen)**: Pull Request から自動的に申請書 HTML を生成する Action の実装。
*   **Phase 3 (Enforcement)**: 本番デプロイ時における Web/A 承認署名の必須化（強制）。

---

本提案は、「Web/A が世界をどう変えるか」を、まず「我々自身がどう変わるか」によって証明する試みである。
