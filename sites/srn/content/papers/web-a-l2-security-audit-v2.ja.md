# セキュリティ監査報告書 v2: Web/A Layer 2 暗号化
**修正後の実装およびサプライチェーンリスクの評価**

## 1. エグゼクティブサマリー
本報告書は、初期の改善対応（パディングの改良、PQCプロバイダー注入のリファクタリング）後に行われた監査結果をまとめたものである。いくつかの戦術的な改善が見られるものの、**根本的なセキュリティ姿勢は依然として脆弱である**。アーキテクチャは制御不能なブラウザ環境におけるクライアント側の完全性に強く依存しており、設計上の前方秘匿性（Forward Secrecy）が欠如している。さらに、プロジェクトの「オープンソース」という性質は、攻撃者による精密なホワイトボックス分析を可能にする一方、外部の暗号ライブラリへの過度な依存は重大なサプライチェーンリスクをもたらしている。

**判定: 高リスク。厳格な運用管理なしに、極秘情報や高額な金融取引データに使用することは推奨されない。**

## 2. 改善対応のレビュー

### 2.1. トラフィック分析の緩和（パディング）
*   **実装**: 0〜255バイトのランダムなパディングを追加。
*   **批判**: **不十分である。** これにより論理値のフラグ（Yes/No）は隠蔽されるが、より大きな入力（例：病歴のテキスト）のサイズを隠す効果はほとんどない。5KBのペイロードと5.2KBのペイロードを観察する攻撃者は、依然としてデータの重要な特徴を推測できる。
*   **評価**: 低い有効性。

### 2.2. PQC プロバイダーの注入
*   **実装**: `globalThis` への依存を排除し、明示的な注入を要求するように変更。
*   **批判**: **責任の転嫁である。** ライブラリが window オブジェクトを暗黙的に信頼しなくなったのは前進だが、それを利用するアプリケーション側が依然として PQC プロバイダーをどこからかロードする必要がある。アプリケーションのローダーが侵害された場合（XSSなど）、攻撃者は関数呼び出し時に悪意のあるプロバイダーを注入するだけでよい。脆弱性はスタックの上層に移動しただけであり、解決されたわけではない。

## 3. 構造的およびアーキテクチャ上の脆弱性

### 3.1. 前方秘匿性（Forward Secrecy）の完全な欠如
**深刻度: 致命的 (CRITICAL)**
プロトコル設計において、**静的な X25519 受信者鍵**が使用されている。
*   **シナリオ**: 攻撃者が今日、暗号化されたトラフィックを傍受する。5年後、組織の秘密鍵が漏洩（内部不正、ラップトップの盗難など）した場合、**過去に遡ってすべての送信内容が即座に読み取り可能になる。**
*   **分析**: 現代のプロトコルのほとんど（TLS 1.3、Signalなど）は前方秘匿性を優先している。Web/A のファイルベース、非同期という性質上、エフェメラルな鍵交換は困難だが、「簡便性」のためにこのリスクを受け入れることは、機密データにとって危険なトレードオフである。

### 3.2. リプレイ攻撃とアグリゲーターへの依存
**深刻度: 高 (HIGH)**
ライブラリは `nonce` を生成するが、**その検証を強制していない**。
*   **欠陥**: `l2crypto` ライブラリは有効なエンベロープであれば盲目的に復号する。ステートレスである。
*   **リスク**: 受け手側のアグリゲーター実装が nonce の追跡を怠った場合、同じ「1000ドルの送金」フォームが500回受理されることになる。プロトコルの安全性は、ライブラリの制御外にある受信側の実装の「正しさ」に完全に依存している。

### 3.3. クライアントサイドの信頼モデルという幻想
**深刻度: 高 (HIGH)**
ブラウザを「信頼できるエージェント」であると仮定している。
*   **現実**: ブラウザは、拡張機能やアドテック・スクリプト、潜在的な XSS ベクトルが蔓延する敵対的な環境である。
*   **攻撃ベクトル**: 暗号化関数に到達する「前」に、`MutationObserver` や `HTMLFormElement.prototype.submit` のフックによってデータを取り出すことは、同じオリジンで実行されている悪意のあるスクリプトにとって容易である。クライアントサイド暗号化は、エンドポイントの侵害に対しては**無防備**である。

## 4. サプライチェーンおよびコードベースのリスク

### 4.1. 依存関係のリスク (`@noble/*`)
プロジェクトは `@noble/curves` と `@noble/hashes` に依存している。
*   **リスク**: `@noble` は定評があるが、単一のメンテナによるエコシステムである。メンテナのアカウント侵害や強制攻撃によって、検出が極めて困難なバックドア（例：コンスタントタイム違反や弱い RNG シード）が混入されるリスクがある。
*   **緩和策の不在**: リポジトリ内で依存関係の固定（ハッシュ検証）やベンダー管理が行われている形跡がない。`npm install` はレジストリを盲目的に信頼している。

### 4.2. ソースコードの公開（ホワイトボックス分析）
ソースが公開されているため：
*   **タイミング攻撃**: 攻撃者は `decryptLayer2` 関数をローカルでプロファイリングし、「整合性チェック失敗」と「復号失敗」の時間差を見つけることで、パディング・オラクル型攻撃の手がかりを得る可能性がある。JavaScript の JIT 最適化により、コンスタントタイム実行を保証することは極めて困難である。
*   **RNG 分析**: `crypto.getRandomValues` に依存している。ブラウザの PRNG が弱い場合、あるいは特定の組み込み環境で侵害されている場合、エフェメラル鍵が予測可能になる。

### 4.3. 知的財産およびライセンスコンプライアンス
*   **リスク**: 複雑な暗号ロジックを実装している。コピーレフト（GPLなど）やプロプライエタリなソースから断片が引用されていた場合、法的訴訟を招く可能性がある。
*   **特許リスク**: ML-KEM-768 (Kyber) の実装には、特定の法域で特許請求がなされているアルゴリズムが含まれている可能性がある。商業利用においてはパテントトロールのターゲットになるリスクがある。

## 5. 実装固有の欠陥

### 5.1. エラーハンドリングによるサイドチャネル
コードは汎用的な JavaScript エラーをスローしている。
```typescript
if (aadObj.layer1_ref !== envelope.layer1_ref) throw new Error("AAD mismatch");
```
*   **脆弱性**: このエラーが捕捉され、下層の AEAD からの「MACチェック失敗」とは異なる形で報告された場合、サイドチャネルとなる。オラクルは「不正なコンテキスト」と「不正な鍵」を区別できてしまう。

### 5.2. JSON 標準化の脆弱性
`canonicalize` (RFC 8785) への依存は壊れやすい。
*   **問題**: JS 環境（クライアント）と Go/Python 環境（サーバー）で、コーナーケース（例：Unicode 正規化形式、浮動小数点の精度）の扱いがわずかに異なるだけで、有効なメッセージが拒絶され、サービス拒否（DoS）を招く可能性がある。

## 6. 推奨事項

### 短期的（即時実行）
1.  **依存関係のベンダー管理**: `npm` に依存しすぎず、`@noble/*` の正確なバージョンをリポジトリに含め、監査すること。
2.  **アグリゲータ仕様の強制**: 仕様において、nonce の追跡を **必須 (REQUIRED)** とすること。参照実装には "ReplayCache" インターフェースを提供すべきである。
3.  **監査ログ**: ブルートフォース攻撃を検知するため、復号イベントを不変な形式でログに記録すること。

### 長期的（アーキテクチャの変更）
1.  **エフェメラル鍵の交渉の導入**: 静的な公開鍵から脱却すること。送信前にワンタイムの公開鍵を取得する「Pre-Key Bundle」サーバー（Signal と同様の仕組み）を実装すること。これにより前方秘匿性を解決できる。
2.  **WebAssembly (Rust/C) への移行**: 高水準の JavaScript で暗号処理を行うのをやめること。検証済みの Rust クレートからコンパイルされた Wasm バイナリを使用し、メモリと実行時間をより厳密に制御（タイミング攻撃への耐性向上）すること。
3.  **厳格な CSP と SRI**: すべてのスクリプトに対して、Content Security Policy ヘッダーと Subresource Integrity を義務付けること。

## 7. 結論
現在の実装は「プライバシー・シアター（プライバシーの劇場）」として機能している。通信路上（TLS が既に行っていること）や静止時（部分的）のデータは保護されるが、鍵管理とエンドポイントセキュリティの本質的なリスクは解決されていない。**低リスクなアンケート調査**には適しているが、**銀行、投票、あるいはクリティカルなインフラ**には不適格である。
